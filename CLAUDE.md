# CLAUDE.md

Istruzioni di progetto per Claude Code su **AI Market Mind**.

## Dove si trova la documentazione di progetto

Ogni riferimento a `Market Mind AI - Docs/...` in questo file (ER diagram, interfacce Pydantic, doc di onboarding per fonte, agenda delle decisioni) punta a una cartella **esterna a questo repository git**, non presente nel checkout: è un vault Obsidian su filesystem locale. Il percorso risolto è:

```
/home/francesco/Documents/Obsidian/Conoscenza/3 - Castello/Progetti Personali/Market Mind AI - Docs
```

Il modo canonico per trovarlo è aprire `MarketMind-AI.code-workspace` in root (gitignored, non versionato: è configurazione locale dell'editor, non del progetto) — dichiara due cartelle radice, `MarketMind-AI` (questo repo) e `Docs` (il percorso sopra). Se il file workspace non fosse presente o il percorso fosse cambiato, è lì che va cercato per primo prima di assumere che la documentazione non esista.

## Workflow git per le sessioni Claude Code

Le sessioni Claude Code che lavorano su questo repo — tipicamente isolate in un worktree separato (`.claude/worktrees/...`) — non pushano mai i propri branch su `origin`/GitHub e non aprono Pull Request su GitHub: il lavoro resta locale. A fine modifiche i commit restano sul branch locale del worktree, già visibile senza bisogno di fetch (i worktree condividono lo stesso `.git`); è l'utente a integrarli nel proprio branch quando vuole, tipicamente con `git merge <branch-worktree>` dal proprio checkout. Nota tecnica per una sessione futura che leggesse questo file: l'harness impedisce a una sessione isolata in un worktree di eseguire comandi git che toccano la cartella condivisa (il checkout principale dell'utente) — quindi anche se richiesto esplicitamente, una sessione così isolata non può eseguire il merge direttamente nel checkout dell'utente; può solo lasciare il branch pronto, committato, e comunicare all'utente il comando da lanciare lui stesso.

## Cos'è il progetto

Piattaforma che simula decisioni finanziarie storiche (BUY/SELL/HOLD) tramite un LLM, usando solo le informazioni disponibili fino a un timestamp storico — nessun look-ahead — e ne backtesta l'esito su un universo di ~500 asset (S&P 500). Documento di riferimento completo: `Market Mind AI - Docs/Market Mind AI.md`.

Le pipeline (`marketmind_pipelines`) sono classi: `BasePipeline` (`base.py`) fissa la sequenza di ogni run — audit (`IngestionRunAudit`) → `setup()` → per ogni target `extract()` → `transform()` (record Pydantic, `records.py`) → `load()` (un sink per tipo di record, `sinks.py`, sopra `TableRepository`: risoluzione `symbol`→`asset_id`, upsert idempotenti, payload grezzo in `raw` nella stessa transazione) → `teardown()`; `PerSymbolPipeline` (un target per ticker, universo di default o `symbols` espliciti, pausa tra i ticker) e `BulkPipeline` (un solo fetch per run) coprono i due casi ricorrenti. L'errore di un target viene isolato; l'esito del run è `success` (nessun target fallito), `partial` (almeno uno, fino al 50% compreso — `failure_threshold`) o `failed` (oltre la soglia, o eccezione fuori dai target, rilanciata). FMP ha come target la coppia (ticker, endpoint), così un endpoint fuori piano fallisce da solo. L'HTTP passa da `HttpSource` (`http.py`): timeout obbligatorio, retry solo su errori di rete/429/5xx (mai su 4xx), chiave API oscurata nei messaggi d'errore (altrimenti finirebbe nei log e in `t_ingestion_runs.error_message`). Entry point unico: `python -m marketmind_pipelines run <nome> [--symbols A,B] [--dry-run]` (registro in `registry.py`; exit 0 per `success`/`partial`, 1 per `failed`, 143 su SIGTERM, convertito in `PipelineInterrupted` così il run si chiude `failed` invece di restare `running`). `--dry-run` lavora su un'unica transazione esterna annullata alla chiusura del `Database`, così audit e dati restano coerenti tra loro (FK `t_audit_logs.run_id`) senza committare nulla. Tutte e otto le pipeline di ingestion previste sono implementate e verificate end-to-end sull'intero stack reale — un'immagine Podman per pacchetto (`deploy/images/`: `marketmind-migrate` con Alembic e le migrazioni, `marketmind-pipelines`, `marketmind-llm-decision-engine`, `marketmind-frontend` ancora senza unit Quadlet; multi-stage, ciascuna installa solo il proprio pacchetto come wheel, runtime senza root; contesto di build filtrato da `.dockerignore`), unit Quadlet `.container` in `deploy/quadlet/<pacchetto>/` (le pipeline con `Exec=run <pipeline>` sull'entry point dell'immagine) e `.timer` in `deploy/systemd/<pacchetto>/` (linkate in `~/.config/systemd/user/` e abilitate esplicitamente da `deploy.sh`, distinte dalle unit Quadlet in `~/.config/containers/systemd/`), trigger manuale (`deploy.sh --trigger <pipeline>`). Le migrazioni girano nel container one-shot `marketmind-migrate` (`RemainAfterExit=yes`), che pipeline e Decision Engine dichiarano in `Wants=`/`After=` e che `deploy.sh` riesegue a ogni deploy prima di abilitare i timer; `deploy.sh --build` costruisce le immagini, `--keep-secrets` rideploya senza ricreare secret né riallineare le password dei ruoli, e ogni deploy rimuove i symlink `marketmind*` che non corrispondono più a nessuna unit del repo. L'ambiente live gira su questo deploy (switch con `deploy/quadlet/deploy.sh --keep-secrets` dal checkout su `main`, DB mai riavviato): ogni symlink delle unit punta a `deploy/` di questo repo, nessuno più al vecchio worktree `.claude/worktrees/ingestion-pipelines`, e l'immagine condivisa `marketmind-ingestion` è stata rimossa. Il modulo `llm/` è implementato: `LLMProvider` (`base.py`) è l'interfaccia generica a cui `decision_engine/` si affida — un `Protocol` con due metodi, `decide(context: dict) -> Decision` e `select_watchlist(context: dict) -> WatchlistSelection` (il bootstrap di un portfolio, non il loop settimanale ordinario); il tipo di `context` resta un `dict` generico in entrambi i casi. `Decision` (`schemas.py`) è l'output strutturato del provider per `decide()` (`decision` BUY/SELL/HOLD, `confidence` opzionale, `reasoning` opzionale, `defer` opzionale — una `DeferralRequest` con cui l'LLM chiede di essere ricontrollato più avanti invece di aspettare la prossima cadenza settimanale); `WatchlistSelection` (`symbols`, `reasoning`) è l'output per `select_watchlist()`, nessuna delle due un'interfaccia di ingestion di `schemas/records.py`. Un fallimento del provider solleva `DecisionError` (`exceptions.py`) invece di un fallback silenzioso, per entrambi i metodi. La prima implementazione, `GeminiProvider` (`gemini.py`), usa l'SDK nativo `google-genai` senza tool-use/function-calling, con `response_schema` (per lo schema del metodo chiamato) lato API più validazione Pydantic locale su `response.text` come controllo finale, retry via `tenacity` sulla chiamata di rete e un timeout esplicito (30s, `http_options`) — senza, un backend che non risponde blocca il processo a tempo indefinito, nessuna eccezione per far scattare il retry. Nonostante il nome, funziona anche con modelli Gemma sullo stesso client (`model` è un parametro del costruttore): verificato con `gemma-4-31b-it`, che incapsula la risposta in un code fence markdown nonostante lo si sia richiesto puro JSON — tollerato da `_strip_markdown_fence()` prima della validazione. Dettaglio in `Market Mind AI - Docs/Decision Engine/00_llm_provider.md`.

Il modulo `orchestration/` non è più vuoto: espone due primitivi generici (`scheduler.py`) su cui `decision_engine/` si appoggerà per rispondere a una `DeferralRequest` — `schedule_transient_run()` (unit systemd transiente via `systemd-run --user --on-active`, mai un `.timer` persistito su disco) e `trigger_ingestion_pipeline()` (`systemctl --user start` sul container Quadlet già esistente di una pipeline, stesso meccanismo di `deploy.sh --trigger`); entrambi sollevano `OrchestrationError` (`exceptions.py`) invece di lasciar propagare `subprocess.CalledProcessError`/`FileNotFoundError` grezze. Nessuna delle otto pipeline di ingestion invoca questo modulo per il proprio funzionamento ordinario. Dettaglio in `Market Mind AI - Docs/Decision Engine/01_rinvio_decisione_e_orchestration.md`.

Il modulo `decision_engine/` è a classi: `DecisionEngine` (`engine.py`, provider LLM scelto tramite una factory e orologio iniettati) contiene solo la logica e parla con Postgres attraverso un `DecisionStore` (`store.py`; `PostgresDecisionStore` sopra i repository di `repositories/` — `MarketContextRepository`, `PortfolioRepository`, `DecisionRepository`, `BacktestRepository`, tutti su `TableRepository` con la policy `APP` —, un'implementazione in memoria nei test unitari). Entry point unico `python -m marketmind_llm_decision_engine run-due | init-portfolio <id> | backtest <portfolio> <run>` (`--dry-run`/`--no-save`), container Quadlet `marketmind-decide.container` (`Exec=run-due`) + timer `marketmind-decide.timer`, cadenza oraria, ruolo Postgres `marketmind_app`. Ogni giro di un portfolio registra il proprio esito su `t_model_runs` con la stessa regola delle pipeline (`run_outcome` in `marketmind_db.audit`: `success`, `partial` se fallisce anche una decisione, `failed` oltre il 50% o per un errore fuori dalle singole decisioni, SIGTERM compreso); la causa di ogni decisione fallita va nei log e in `error_message`. Un portfolio `'model'` va prima inizializzato (`DecisionEngine.initialize_portfolio(portfolio_id)`, comando `init-portfolio`) — un bootstrap esplicito, non automatico, pensato per un front-end futuro, in un solo passo: sceglie con un'unica chiamata `select_watchlist()` (non `decide()`) quali asset dell'universo osservare, dati l'universo intero e la strategia del portfolio (`t_portfolios.strategy_prompt`, persistente e obbligatoria per un 'model'), sostituisce la sua watchlist (`portfolio.t_portfolio_watchlist`) con la selezione — un replace totale, non un merge; un `symbol` non riconosciuto viene scartato con un warning — e subito dopo gira un primo giro di `decide()` sulla watchlist appena scelta, riusando lo stesso provider: un portfolio appena attivato ha da subito un giudizio (anche `HOLD`) su ogni asset che osserva, non aspetta il prossimo giro dovuto. Le decisioni sono poi portfolio-aware: cash e posizioni correnti di un portfolio influenzano la decisione BUY/SELL/HOLD stessa (non solo cosa farne dopo), e ogni portfolio è isolato dagli altri — proprio provider/modello, propria strategia, propria watchlist, nessuna funzione del Decision Engine legge mai lo stato di più di un portfolio insieme. L'Historical Context Builder (`ContextBuilder`, `context_builder.py`, finestre in `ContextWindows`) costruisce un `DecisionContext` (`schemas.py`, sei sezioni: prezzi/news/eventi macro/eventi societari più `portfolio` — cash, posizioni, strategia) per un asset, un portfolio e un `as_of` esplicito (default: ora, mai calcolato internamente — riusabile da un futuro rinvio o da un futuro Backtesting Engine), con finestre di default v1 strette e sempre parametriche: prezzi ultimi 30gg, news ultimi 7gg (max 20/asset), eventi societari ultimi 90gg, eventi macro solo l'ultimo valore noto per indicatore. Il loop (`DecisionEngine.run_due()`) itera solo i portfolio `'model'` attivi il cui giro è davvero dovuto ORA (`PortfolioRepository.due_model_portfolios` — `t_portfolios.next_decision_at` nullo o scaduto, non semplicemente "attivo"; il benchmark resta escluso per disegno) e per ciascuno costruisce provider (`llm/factory.py`, `get_provider(name, model)` — necessario perché `decision_engine/` non deve mai importare un'implementazione di provider concreta), `ModelRun` (con `portfolio_id` obbligatorio) e decisioni isolatamente, scoperto sulla watchlist del portfolio (non l'universo condiviso); un portfolio mai inizializzato produce zero decisioni, non un errore; un errore isolato a un portfolio o a un singolo asset non blocca gli altri. La cadenza è per-portfolio, non per-timer: dopo ogni giro completato (bootstrap incluso) il motore stesso schedula quando tornare a girare per quel portfolio (`PortfolioRepository.schedule_next_decision()`, default `DEFAULT_DECISION_INTERVAL`, 7 giorni) — un timer condiviso invoca `run_due_decisions()` più spesso del necessario, filtrando da solo chi è scaduto; solo un giro `success` o `partial` fa avanzare `next_decision_at`: un giro `failed` (modello non disponibile, quota LLM esaurita) lascia il portfolio scaduto, riprovato al prossimo scatto orario del timer. Un `BUY`/`SELL` non resta un giudizio: viene eseguito subito, nella stessa transazione della `ModelDecision`: `plan_trade` (`decision_engine/trading.py`, funzione pura) calcola il nuovo stato e `PortfolioRepository.apply_trade` lo scrive — aggiorna `t_portfolios.cash` e crea/aggiorna/cancella la riga in `t_portfolio_positions` (media pesata sul prezzo di carico per un BUY, rimozione della riga per un SELL che azzera). La size del trade (`Decision.size_pct`, 0-1, obbligatoria per BUY/SELL e vietata per HOLD via `model_validator`) è proposta dall'LLM stesso, non una regola deterministica — persistita anche su `t_model_decisions` per audit. Prezzo di esecuzione: l'ultimo noto nel context (`context.prices[-1]`), mai un dato futuro; nessun prezzo disponibile, o ultima barra più vecchia di `DEFAULT_MAX_PRICE_AGE` (3 giorni, copre il weekend) → decisione registrata ma trade saltato con warning. Le decisioni sull'intera watchlist di un run si eseguono in sequenza: il cash disponibile per un asset tiene già conto delle allocazioni fatte sugli asset precedenti nello stesso run, non un piano unico su tutta la watchlist. `equity_value` non viene ricalcolato (richiederebbe il mark-to-market di tutte le posizioni, non solo di quella scambiata — punto aperto). La registrazione di decisione e trade (`PostgresDecisionStore.record_decision`) è avvolta in `track_model_run(run_id)` (`marketmind_db/run_context.py`): la sessione aperta al suo interno imposta da sé la GUC `marketmind.model_run_id`, così i trigger di snapshot del portfolio collegano cash/posizione al run che li ha originati — necessario perché il Backtesting Engine (proof of concept, dettaglio sotto) possa isolare i trade di un run specifico. Il Backtesting Engine non possiede l'esecuzione: resta un motore di analisi retrospettiva (Sharpe/drawdown/PnL su un periodo, via vectorbt) su decisioni già eseguite. Le query verso `market_data`/`portfolio` e le scritture verso `decisions`/`portfolio` vivono nei repository di `repositories/`, mai in `decision_engine/` direttamente. `GeminiProvider` riprova gli errori 5xx e di rete, e i 429 la cui attesa indicata da Google (`RetryInfo.retryDelay`, o il "retry in Xs" del messaggio) è entro `MAX_RATE_LIMIT_WAIT_S` (5 minuti: i limiti al minuto, richieste o token di input) aspettando quel tempo; gli altri 4xx e i 429 con attesa più lunga (la quota giornaliera, ore all'azzeramento) restano definitivi. Tre portfolio reali esistono nell'istanza di sviluppo: `spy-benchmark` (benchmark), `gemini-baseline` (capitale iniziale $100.000, `gemini-3.6-flash`, strategia generica, watchlist di 25 asset — più della quota free di 20 richieste/giorno) e `gemma-growth-test` (capitale iniziale $20.000, `gemma-4-31b-it`, strategia growth/tech, watchlist di 10 asset). Entrambi hanno decisioni e trade reali; `gemma-4-31b-it` (come `gemma-4-26b-a4b-it`) risponde oggi `500 INTERNAL` lato API Google sulle decisioni reali, quindi i giri di `gemma-growth-test` risultano `failed` e vengono riprovati ogni ora finché il modello non torna disponibile. Dettaglio in `Market Mind AI - Docs/Decision Engine/02_context_builder_e_motore.md`, `03_bootstrap_e_watchlist.md`, `04_esecuzione_trade.md` e `05_timer_e_cadenza.md`.

Il modulo `backtest/` è un proof of concept: `Backtester.run(portfolio_id=, run_id=, as_of=)` (`engine.py`, sopra un `BacktestStore`; la parte vectorbt è la funzione pura `compute_metrics`) ricostruisce gli ordini eseguiti da un run leggendo `t_portfolio_position_snapshots` filtrata per `(portfolio_id, run_id)` (`BacktestRepository.position_events()`) e li rigioca su `vectorbt.Portfolio.from_orders(cash_sharing=True)`, lo stesso disegno multi-asset di produzione fin da questa prima versione. Supporta solo eventi `operation='INSERT'` (un primo BUY su una posizione vuota, dove `avg_price` coincide col prezzo di esecuzione esatto): `UPDATE`/`DELETE` sollevano `NotImplementedError` invece di produrre numeri silenziosamente sbagliati, nessun run reale li ha ancora prodotti. Le quattro metriche (PnL, Sharpe, max drawdown, win rate — `NaN` convertito a `None`) si scrivono su `t_backtest_results` via `BacktestRepository.write_result()`, mai upsert; comando `backtest <portfolio> <run> [--no-save]`, che importa vectorbt solo lì (nell'immagine `NUMBA_CACHE_DIR` punta a una directory scrivibile, il container gira senza root). Verificato end-to-end contro dati reali: `gemma-growth-test`/run 41, riga scritta in produzione (numeri rumorosi, il trade è di poche ore fa — la meccanica è validata, non ancora la significatività statistica). `vectorbt` richiede `plotly<6` fissato in `pyproject.toml` (la libreria, ferma da tempo, importa a caricamento un tema incompatibile con Plotly ≥6). Dettaglio in `Market Mind AI - Docs/Backtest/00_motore_backtest.md`.

Il collegamento `run_id` sui trigger generici via GUC di sessione (`marketmind.ingestion_run_id`/`marketmind.model_run_id`, documentato fin da `0001`/`0002`) restava scoperto: nessun codice lo impostava, ogni riga storica in `audit.t_audit_logs`/`t_portfolio_snapshots`/`t_portfolio_position_snapshots` aveva `run_id` sempre NULL. `db/session.py` espone ora `track_ingestion_run()`/`track_model_run()` (due `ContextVar`, non parametri su `get_session()`): `IngestionRunAudit` (`marketmind_db/audit.py`) e `decision_engine/engine.py` li usano, ogni `get_session()` aperta al loro interno imposta la GUC da sé, zero cambiamenti richiesti alle otto pipeline. Storico pre-fix non backfillato per `audit.t_audit_logs` (88.384 righe, rischio concreto di attribuzione sbagliata su run sovrapposti/hypertable chunk-naming), backfillato a mano solo per le 8 righe reali di `gemma-growth-test`/run 41. Dettaglio completo in `Market Mind AI - Docs/tasks/2026-09-14-run-id-guc-linkage.md`.

Il modulo `dashboard/` è implementato in v1: `dashboard/app.py` (`streamlit run`, unico entry point standalone del modulo) mostra, per un portfolio scelto in sidebar tra tutti quelli esistenti (`model`/`benchmark`, attivi o sospesi — `dashboard_reader.py` del pacchetto frontend, `list_portfolios()`), lo stato corrente (cash, capitale iniziale, costo delle posizioni aperte), le posizioni, la watchlist (solo `model`), il cash nel tempo e il log decisioni con reasoning (`get_cash_history()`/`get_decision_log()`). Il grafico più prominente è etichettato onestamente "cash nel tempo", non equity curve: `equity_value` non è ricalcolato a ogni trade (v. Ambiguità aperte), quindi mostrarlo sarebbe fuorviante — solo `cash` riflette davvero i trade eseguiti. Niente Sharpe/drawdown di periodo né confronto col benchmark, rimandati: pochi run di backtest reali oggi. Le funzioni che costruiscono le strutture dati mostrate sono pure e testate senza runtime Streamlit; `_render()`/`main()` non hanno test propri, stesso limite accettato per gli entry point delle pipeline di ingestion. Verificato end-to-end (screenshot reali contro i tre portfolio esistenti). Solo locale per ora (`uv run streamlit run packages/marketmind_frontend/src/app.py`) — containerizzazione/Quadlet rimandati a un'iterazione successiva, scelta esplicita. Dettaglio in `Market Mind AI - Docs/Dashboard/00_dashboard.md`.

Con questo, tutti i moduli applicativi previsti hanno almeno un primo giro di implementazione — nessuno resta "non ancora iniziato"; `backtest/`/`dashboard/` restano proof of concept da estendere, non moduli finiti.

## Stack

- **Linguaggio**: Python
- **Database**: PostgreSQL + TimescaleDB — tabelle normalizzate, niente pipeline di riprocessamento bronze/silver a più stadi (raffinata e payload grezzo restano scritti nella stessa transazione dallo stesso script di ingestion); il payload grezzo, dove preservato, vive in una tabella dedicata di uno schema separato (`raw`), non inline sulla tabella raffinata
- **Validazione dati**: Pydantic
- **ORM/migrazioni**: SQLAlchemy + Alembic
- **Backtesting**: vectorbt, con `cash_sharing=True` — analisi retrospettiva delle prestazioni (Sharpe/drawdown/PnL) su decisioni già eseguite da `decision_engine/`, non simulazione dell'esecuzione: quella avviene per davvero al momento della decisione, non a valle
- **Dashboard**: Streamlit, connessa direttamente a Postgres via SQLAlchemy
- **Orchestrazione**: nessun tool dedicato — script Python + timer systemd
- **Container**: Podman rootless via systemd Quadlet, deploy automatizzato da `deploy/quadlet/deploy.sh`; target futuro: server NixOS con `virtualisation.oci-containers`. Per il momento sviluppo localhost. Rete Podman condivisa `marketmind.network` (`Market Mind AI - Docs/Architettura/05_networking.md`) attiva e verificata: `marketmind-db` la usa già, i futuri container di ingestion la raggiungeranno come `marketmind-db:5432` via il DNS integrato di Podman. Direzione CI/CD (GitHub Actions) ancora aperta, vedi `Market Mind AI - Docs/Architettura/02_ci_cd.md`.
- **Provider LLM**: Gemini per la prima implementazione, dietro un'interfaccia generica (`llm/base.py`); nuovi provider si aggiungono come moduli affiancati senza toccare `decision_engine/`.

## Regole architetturali da rispettare

- Ogni script di ingestion deve produrre output conforme a una delle interfacce Pydantic in `Market Mind AI - Docs/Data Providers/00_schema_interfacce.md` (`AssetRecord`, `MarketPriceRecord`, `NewsEventRecord`, `MacroEventRecord`, `CompanyEventRecord`, `UniverseMemberRecord`) prima di scrivere su Postgres — mai il payload grezzo direttamente.
- Le interfacce di ingestion usano `symbol`/`indicator` come identificatore naturale, non `asset_id`: la risoluzione all'id interno avviene nello strato di scrittura/upsert in `db/`, non negli script di ingestion.
- GDELT: usare il dataset Web NGrams per la copertura ampia sui 500 asset, non la DOC API — il rate limit di 1 richiesta/5s la rende impraticabile a quella scala. L'entity linking articolo → asset si basa su un match testuale tra nome azienda/ticker e il `QUADGRAM` estratto dal flusso Web NGrams, nessun servizio NLP dedicato. Dettagli in `Market Mind AI - Docs/Data Providers/02_gdelt_onboarding.md`.
- Dati macro FRED: si usano i valori vintage via l'API ALFRED (`realtime_start`/`realtime_end` impostati al momento della query), non le serie standard riviste nel tempo — necessario per coerenza col principio no-look-ahead del progetto.
- Cadenza e storico: il motore decisionale genera decisioni con cadenza per-portfolio (default 7 giorni, `t_portfolios.next_decision_at`, scritta dal motore stesso — non un cron fisso), scoperte sulla watchlist di ciascun portfolio, non sull'intero universo indiscriminatamente (un trigger event-driven resta una direzione futura, da valutare in base a costi/risultati osservati sulla cadenza attuale); i prezzi si accumulano a granularità intraday (oraria); nessuna fonte prevede un backfill storico profondo — l'ingestion parte da subito e accumula i dati in avanti.
- Retention: safeguard di un anno su tutte le tabelle soggette a rotazione, da rivedere in base a test futuri e alla mole dati reale.
- Naming conventions di schema (nomi tabella/colonna/vincolo/indice) sono fissate in `Market Mind AI - Docs/db/01_schema_dati_er.md` § Naming conventions — in particolare la `naming_convention` esplicita su `MetaData` (`pk_<table>`, `fk_<table>_<column>_<ref_table>`, `uq_<table>_<column>`, `ck_<table>_<constraint_name>`) e il prefisso `i<access_method>_` per gli indici creati esplicitamente. Non introdurre nomi impliciti generati da Postgres/SQLAlchemy.
- Ogni pipeline di import ha il logging abilitato: ogni entry point standalone chiama `marketmind_common.logging_config.configure_logging()` all'avvio (mai i moduli di libreria, per non duplicare handler). Convenzione completa su livelli/destinazione in `Market Mind AI - Docs/Architettura/04_logging.md`.
- Le pipeline esposte a rate limit gestiscono retry/backoff tramite `tenacity` (decoratori `@retry`, parametri configurati per pipeline secondo la forma del limite specifico), non un modulo custom.
- Sviluppo in TDD: test prima, implementazione dopo. `pytest`+`pytest-mock` (dev dependency), test in `tests/unit/` (nessun accesso a DB/rete — tutto ciò che è esterno è mockato) e `tests/integration/` (marcati `@pytest.mark.integration`, richiedono `marketmind-db` raggiungibile). La fixture `db_session` (`tests/conftest.py`) lega la sessione a una transazione con rollback automatico anche sui `commit()` del codice sotto test — dove il codice apre le proprie sessioni (`get_session()` a livello di modulo, non iniettata) il test scrive per davvero e pulisce esplicitamente a fine test, la fixture non può intercettare una connessione diversa dalla propria. Comando: `uv run pytest tests/` (tutto), `uv run pytest tests/unit/` (senza DB).

## Schema dati

Diciotto tabelle in cinque schema Postgres separati: `market_data` (`t_assets`, `t_market_prices` hypertable, `t_news_events`, `t_macro_events`, `t_company_events`, `t_universe_members` — universo osservato, ~500 titoli + benchmark SPY, distinto dal sottoinsieme su cui gira davvero il motore decisionale via `is_benchmark`), `raw` (`t_news_events_raw`, `t_company_events_raw` — payload grezzo separato dalle rispettive tabelle raffinate, relazione 1:1 con FK `ON DELETE CASCADE`), `decisions` (`t_model_runs`, `t_model_decisions`, `t_backtest_results`), `portfolio` (`t_portfolios`, `t_portfolio_positions`, `t_portfolio_snapshots`, `t_portfolio_position_snapshots`, `t_portfolio_watchlist` — tracking del portafoglio virtuale più lo scope di asset osservati da ciascun portfolio 'model'; separato da `decisions` perché il portafoglio è lo stato che risulta dalle decisioni, non una decisione), `audit` (`t_ingestion_runs`, `t_audit_logs` — logging e auditing operativo). Nessuna delle tabelle di ingestion conosce strutturalmente le fonti dati: la provenienza vive solo in `source`/`fetched_at`, mai nella struttura delle colonne, così da poter sostituire o aggiungere fonti senza modificare lo schema. `t_audit_logs` è popolata da un trigger Postgres generico, non dallo strato applicativo — `t_universe_members`, mutabile e di ingestion come le altre cinque di `market_data`, rientra in questo meccanismo generico (a differenza di `raw`/`portfolio`, escluse per motivi diversi: insert-only le prime, per evitare doppio logging le seconde). Lo schema `raw` è separato per generalizzare il pattern a future tabelle di payload grezzo, non per permessi differenziati realmente in vigore oggi: `marketmind_ingestion` ha lo stesso `GRANT` su `market_data` e `raw`. ER diagram completo, tipi, chiavi e indicizzazione in `Market Mind AI - Docs/db/01_schema_dati_er.md`.

## Ambiguità aperte — non assumere, segnalare

Finestre di default dell'Historical Context Builder decise (v1 stretta, dettaglio sopra); resta aperto solo il *come* un futuro motore più agentico renderebbe disponibile all'LLM il retrieval di più storico o di eventi di aziende correlate a runtime — sempre e solo una query ad-hoc su Postgres, mai un'ingestion, ma legato a un tool-use non ancora progettato (richiede un provider con function calling/tool-use affidabile, oggi assente per scelta in `GeminiProvider`). Le decisioni sono ora portfolio-aware (cash/posizioni nel context package) e la size del trade è proposta dall'LLM stesso (`Decision.size_pct`), ma senza alcun limite di allocazione/concentrazione imposto — un portfolio può ricevere BUY su un asset già ampiamente sovrappesato, nessuna regola lo impedisce oggi; se e dove introdurre limiti del genere non è deciso. `t_portfolios.equity_value` non viene ricalcolato quando si esegue un trade (richiederebbe il mark-to-market di tutte le posizioni del portfolio, non solo di quella appena scambiata) — lasciato esplicitamente aperto, non approssimato. Il bootstrap di un portfolio (`initialize_portfolio()`) non ha alcun limite alla dimensione della watchlist scelta (verificato: con una strategia generica l'LLM ha selezionato l'intero universo) e non è previsto rieseguirlo automaticamente — resta un passo manuale. Automazione CI/CD del deploy container via GitHub Actions: runner self-hosted sul server di destinazione vs. runner GitHub-hosted con deploy via SSH, gestione dei secret nel workflow, eventuale build custom delle immagini — bloccata a monte dall'assenza di un server di destinazione diverso da `localhost` (dettaglio in `Market Mind AI - Docs/Architettura/02_ci_cd.md`). Networking: il caso "più container sullo stesso host" è risolto — resta aperto solo il caso di un server remoto. Ruolo di `orchestration/`: deciso — libreria condivisa per il rinvio delle decisioni LLM (`Market Mind AI - Docs/Decision Engine/01_rinvio_decisione_e_orchestration.md`); restano aperti due dettagli tecnici, come i parametri ad-hoc (simbolo, finestra) raggiungano il container Quadlet già esistente di una pipeline (unit systemd "template" per istanza contro un bypass diretto via `systemd-run`/`podman run`) e dove persistere una `DeferralRequest` su `t_model_decisions` (colonna dedicata o dentro `context_snapshot`/`reasoning`) — oltre alla parametrizzazione stessa delle otto pipeline esistenti (quali parametri per ciascuna), confermata come direzione ma non ancora implementata. Test di integrazione: il simbolo sintetico `TESTX` resta solo in `tests/integration/test_dashboard_reader.py`, con scritture reali e pulizia manuale — tutti gli altri (pipeline, `marketmind_db`, Decision Engine) usano le fixture `rollback_*` di `tests/conftest.py` — un fallimento di cleanup in uno qualunque può lasciare dati reali che fanno fallire in cascata molti altri file alla corsa successiva (già capitato una volta, causa un `ON DELETE` mancante su `t_audit_logs.run_id`, chiuso da `0015`). Nessun meccanismo impedisce oggi a un test di lasciare per sbaglio un asset fittizio in `market_data.t_universe_members`, dove un timer reale (es. `gdelt-ngrams`) lo tratterebbe come un asset vero e lo alimenterebbe indefinitamente — già capitato una volta (`TESTSPY`, 9 giorni, 2.306 righe spurie, ripulito il 23-09-26), non un rischio strutturalmente eliminato. Promemoria operativi non bloccanti: verificare se il reset dei 250 req/giorno del piano free FMP è giornaliero o su finestra mobile; vincolo di licenza "uso non commerciale" del piano free Finnhub, da monitorare se lo scope del progetto cambiasse; il piano free di Gemini ammette solo 20 richieste/giorno per modello (verificato con un test end-to-end reale, `Market Mind AI - Docs/tasks/2026-09-13-decision-engine-e2e-test.md`) — insufficiente anche solo per un run di verifica sull'universo attuale (25 asset), un piano a pagamento sarà necessario prima della cadenza settimanale reale.

## Convenzioni di documentazione
